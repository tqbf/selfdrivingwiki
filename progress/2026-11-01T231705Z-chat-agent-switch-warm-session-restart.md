# Chat agent switch now restarts the warm session

## Progress

When a user changed the agent (provider + model) for an existing chat, the composer showed the new selection at once, but the next message still ran on the old provider and model. `ProviderSelector.selectRow` writes the new selection to the chat row, so the app side was correct. The daemon kept the chat's agent runtime warm across turns: `DaemonChatController` captured `runtimeStartRequest` at the first start and cleared it only on close. `processQueueIfPossible` returned that captured request on every warm drain, so the fresh row values were never read while the session stayed warm.

The fix adds a stale-session check to `processQueueIfPossible`, after the quiescence guards and before the `.preparing` claim:

- The controller now records the chat row's provider/model pin (`runtimeStartRowSelection`) when a cold preparation reads the row.
- On a warm drain, it reads the row again. If the pin changed, it runs the same idle close that `stopSession` uses (`record(.sessionClosed)`, clear the pending permission, `closeRuntimeAndRotateGeneration`), then continues the drain. The fresh preparation reads the new row values, and the turn starts on a new runtime.
- The mismatch also clears `chat.acp_session_id`. A resumed ACP session cannot honor a changed provider, and the resume path never applies a changed model, so a resume would silently keep the old agent. A fresh start rebuilds context through the continuation preamble — the same posture as a failed or collected resume. Both provider-only and model-only mismatches clear it.

Two findings shaped the comparison. First, the captured start request holds the runtime's resolved selection, not the row's pin: a nil row pin resolves to the stage default (`LauncherChatAgentRuntime.prepareStart`), and thinking model variants remap the model. A direct request-vs-row comparison restarts every warm turn of every chat without a row override — the `coldStartUsesOneAuthoritativeRuntimePreparation` contract test caught this — and would loop restarts for model-variant providers. The pin-at-capture comparison has no false positives. Second, a store read added at the dispatch capture site, before `startEventLoop`, deterministically flipped the timing in `syncUpdatesUseConsecutiveSequencesAndIgnoreLastActivityOnlyCompatibilityRefresh` and `transportCloseRotatesRuntimeAndRecoversOnNextTurn`; capturing inside the existing cold-path row read adds no store calls and no suspension points, so the drain timing stays unchanged. Also: do not add `.timeLimit` to this suite. Swift Testing wraps each test body in a raced child task to enforce the limit, and that alone flipped those two tests (verified with the annotation as the only change). The suite stays serialized through its `@MainActor` isolation.

Known limitation (narrowed by the final round): the daemon fully restarting after a switch is now handled for both mismatch kinds — a provider switch fails cross-binary resume and falls back to a fresh start with the continuation preamble, and a model switch resumes the old session with the new model applied by the launcher. What remains open is session provenance on the row: the row does not record which provider/model created the stored session, so the controller compares against the pin captured at start (lost on daemon restart) rather than durable provenance.

An independent review round (GPT-family model, two majors) found two gaps in the first cut, both verified against the code and fixed. First, `terminateSessionForShutdown` takes `.shutdown` ownership unconditionally, and it can interleave the mismatch restart's `closeForSettlement` await; the unfenced close then called `finishRuntimeClose`, which restored `.idle` and erased shutdown, letting the drain start a fresh runtime after shutdown began. `closeRuntimeAndRotateGeneration` now fences its close on the `ClosingContext` operation identity: a close whose ownership was stolen mid-await returns false without touching ownership, and the thief's own teardown proceeds; the mismatch drain continues only when the close returned true and `isShutdown` is still false, so a queued follower stays durable and unpromoted. The fencing also covers the `stopSession`, `closeIfIdle`, transport-close, and preflight callers, whose un-contended behavior is unchanged. Second, the close cleared the captured pin and request before the fallible `updateChatAcpSessionId(nil)` write, so a thrown write aborted the drain with the mismatch memory gone and the stale resume id still persisted — the next drain would resume the old agent. The write now happens first: a thrown write rethrows without closing, so the next drain retries the mismatch and the submission fails visibly instead. The re-review confirmed both original majors closed and raised the `closeIfIdle` clobber this note had flagged as open: its tail wrote `ownership = .idle` after a stolen close and returned true, so the host evicted the controller mid-shutdown and later submits stopped throwing `shutdownStarted`. `closeIfIdle` now returns false on a fenced-out close without touching ownership or recovering the queue; only the finished-the-close path keeps the quiescence checks and the idle tail. `stopSession` already treated a false close correctly (it skips recovery) and needed no change. With this closed, only shutdown's entry-write clobber of non-`.closing` owners remains — unchanged and pre-existing.

A sixth review round (MEDIUM) found that the confirmation compared exact strings, but the config-option resolver intentionally normalizes picker effort variants: a pin like `gpt-5.6-luna[high]` may validly apply as — or already be current as — the base `gpt-5.6-luna` (exact advertised value preferred, base form fallback; `ACPModelConfigOptionResolver.swift` 68–87, contract pinned in `AgentProviderModelPickerTests`). Exact-string confirmation false-negatived those correctly configured sessions, closing a working resumed session and losing context for nothing. `resumedSessionModelConfirmed` now compares each outcome against the requested id AND its base form, computed by the resolver's own `baseModelId(fromEffortVariant:)` so the normalization rule cannot drift. A first cut of the comparison matched nil outcomes against the nil base form; the decision-table tests caught it immediately (a nil outcome now never records anything), which is why the table exists. Plain-id behavior is unchanged.

A fourth review round found a HIGH gap in the apply-on-resume: `applyModelIfNeeded` can be a silent no-op. An agent that advertises no model seam lands on the resolver's `useAgentDefault` and mutates nothing, while the daemon now KEEPS the resume id on model-only switches — so the resumed session would silently continue on the OLD model, recreating the stale-model bug. The fix is confirm-or-fall-back. After the apply, the launcher re-reads the post-apply state (`modelsInfo(for:)` + `sessionConfigOptions(for:)`) and decides with a pure helper, `ACPBackend.resumedSessionModelConfirmed(requested:current:appliedConfigOptionValue:)`: nil/empty requested → confirmed (agent-default is the selection); otherwise confirmed only when an apply OUTCOME records the requested id — the `setModel` path refreshes `modelsInfo.currentModelId` (#834 HIGH-#1, ACPBackend 1102–1109) and the config-option path patches the `"model"` select's `currentValue` instead (ACPBackend 1039–1043, which is why the re-read alone is not sufficient for config-option agents). An agent reporting neither signal performed no mutation. Unconfirmed means the resumed session cannot honor the pin: the launcher closes it via `ACPBackend.closeSession` (removes the resume target and clears `resumableSessionId`, so future continues cannot retry it; the subprocess stays alive for the cold start), clears the row's resume id through the shared resume-failed clearing path (its log message now covers both cases), and lets the existing fresh-start branch run — it spawns with the pinned model via the launch profile, the same context-loss posture as a failed resume.
