# #1422: mid-run exit-0 runner death — diagnosis + guard

## The crash reports (lead 1)

Nine `swiftpm-testing-helper-*.ips` files existed in
`~/Library/Logs/DiagnosticReports/` (Oct 10-14), all `parentProc: swift-test`:

- **6× EXC_GUARD, GUARD_TYPE_FD, CLOSE** — exception message e.g. "CLOSE on
  file descriptor 55 (guarded with **0x08fd4dbfade2dead**)". That guard id is
  **libsqlite3's guarded-fd guard** (Apple Developer Forums 84034, SO
  32429431) — NOT a `POSIX_SPAWN_CLOEXEC_DEFAULT` guard as PR #1420's note
  guessed. Crashing threads:
  - 3× `ExtractorPackageStoreCoordinator.openAndLock()` ←
    `ExtractorPackageStoreMultiprocessTests.storeRootReplacementCannotCreateSecondLockDomain`
  - 2× `DirEnumEntryFree` (CoreServices) under `ManagedExtractorFixtureLocator.locate`
  - 1× `-[NSConcreteFileHandle _monitor:]` dispatch-source cancel
- 2× EXC_BREAKPOINT — ordinary Swift traps (SwiftUI env read; array
  `#expect` subscript OOB in `AgentEventTranscriptTranslatorTests`).
- 1× SIGQUIT (Oct 14 21:14) — a killed helper, unrelated.

## Root cause of the EXC_GUARD class (fixed)

`openAndLock` (Sources/WikiFSCore/Extractor/ExtractorPackageStore.swift)
closed its descriptor inside the `do` on the contended path and re-closed it
in the `catch`, guarded only by `fcntl(descriptor, F_GETFD)`. `F_GETFD`
cannot detect **reuse**: between the two closes any other thread (SQLite
opens constantly — the host runs 50+ threads) can take the freed number, and
the catch then closed the **foreign** descriptor. When the reuse winner was
a SQLite open, closing libsqlite3's guarded fd raised EXC_GUARD (CLOSE) and
killed the helper. The crashing test drives the contended path ~200×/run.
Same hazard class the `prepareStoreRoots` failure path was already written
to avoid (see its comment). The other two victim sites (DirEnum, FileHandle)
are explained by the same premature-close shape elsewhere: victim's fd
closed early, number reused by SQLite, victim's later close hits the guard.

Fix: the catch is the descriptor's single owner; the body never closes it
before throwing (commit `fix(extractor): close the store-authority
descriptor on exactly one path`).

## Mechanism: helper death → exit 0 (lead 2)

Forced-death demonstration (this session): started the opt-in run, SIGKILLed
the helper mid-hosted-suite: `swift test` **exited 0**; the dead bundle's
run had printed "Test run started." but no summary; the parent simply moved
on / finished. So the SwiftPM driver treats a vanished helper (EOF on its
channel) as bundle-complete and does not propagate the loss — the summary
deficit is the only visible signal. The shipped gate reads that signal.

## The run-summary gate (lead 3b) — shipped

- `scripts/lib/test-run-summary-gate.sh` — reconciles "Test run started"
  vs "Test run with" counts; any deficit (or a log with no test-run lines
  at all) fails loudly. Pure, unit-tested
  (`scripts/tests/test-test-run-summary-gate.sh`, 8 assertions).
- `scripts/test-optin-app-tests-reconciled.sh` — guarded opt-in entry point
  (sets `WIKIFS_APP_TESTS=1`, tees the log, applies the gate, nonzero exit
  on deficit).
- Standalone from #1427 (was OPEN/unmerged; its sentinel doesn't exist on
  main). The two gates are independent and stack on the same log.

## Natural recurrence AFTER the fix — honest bound

The same session's full opt-in run reproduced the issue signature exactly
(**11 run-starts / 10 summaries**, mid-graph app-bundle run stopping after
6171 log lines in hosted suites) and **the gate failed the invocation**
(exit 1). No new `.ips`; unified log shows no jetsam/runningboard kill in
the window — the helper's workspace was invalidated with no crash report
(SIGKILL produces none). So the death family has at least one more member
without a crash report; it needs dynamic tooling (lldb attach / `log stream`
during a repro). The `com.selfdrivingwiki.debug:store` line "Invariant
violation [scope.parent.invalid] owner=scope.lifecycle: A wiki context does
not have a process parent" appeared in a concurrent helper near the window
and is a lead. The guard makes every such death loud regardless of cause.

## Leak angle (lead 4) — identified, filed as #1430

The leaked node/claude-agent-acp trees match the three `ACP_SMOKE=1`-gated
live tests (real `npx @agentclientprotocol/claude-agent-acp`), not an
un-stubbed sibling; all other `AgentLauncher()` uses stub
`resolveBackend`, and `DaemonWorkloadClient` tests inject proxies. Their
teardown doesn't kill the spawned tree when the agent wedges. Details +
fix direction in #1430.
