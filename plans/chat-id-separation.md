# Goal

Introduce a public `ChatID` namespace for persisted chat entities and migrate internal Swift APIs from chat-valued `PageID` to `ChatID`. Preserve every existing SQLite, JSON, daemon, CLI, File Provider, wiki-link, path, log, and agent-facing raw representation without a schema migration or user-visible behavior change.

# Implementation Summary

Add `ChatID` as a leaf value type in `WikiFSTypes`, matching the existing `PageID` raw-value and primitive-string Codable contract. Apply it by semantic identity rather than broad replacement: persisted conversation IDs and `chat_messages.chat_id` become `ChatID`, while `ChatMessage.id` remains `PageID` under this issue's scope. Keep `AcpSessionID`, `QueueItem.ID`, `WikiID`, bookmark node IDs, and draft enum cases unchanged.

The migration follows the completed `PageID`/`SourceID` split documented in `plans/page-source-id-separation.md`: first freeze compatibility with literal legacy fixtures, then convert models and store contracts, then propagate the type through daemon/session/UI/projection/CLI boundaries, and finally enforce the namespace with real-module compiler fixtures and a narrow chat API signature manifest. Build and test only through command-line SwiftPM.

Primary touch points:

- New `Sources/WikiFSTypes/ChatID.swift`; existing `Sources/WikiFSTypes/PageID.swift`
- `Sources/WikiFSCore/Core/ChatModels.swift`, `WikiSelection.swift`, `BookmarkNode.swift`, and chat rendering/navigation types
- Chat requirements in `Sources/WikiFSCore/Store/WikiStore.swift`, implementations and GRDB row boundaries in `GRDBWikiStore.swift`, and adapters in `WikiStoreModel.swift`
- `Sources/WikiFSEngine/ChatXPCRequests.swift`, daemon event envelopes, `Sources/wikid`, and app-side remote session/coordinator code
- Chat projections in `WikiFSFileProvider`, chat commands in `WikiCtlCore`, and relevant `WikiFS` views/routes
- `Tests/WikiFSTests` and `Tests/WikiFSAppTests`, including compiler fixtures and a new chat API signature manifest
- Documentation index and progress artifacts: `PLAN.md`, a new `plans/chat-id-separation.md`, and `PROGRESS.md`

Scope boundaries:

- Do not alter SQLite schema versions, tables, columns, indexes, foreign keys, or stored ULID text.
- Do not alter `[[chat:<ULID>|Title]]`, daemon JSON keys or values, CLI syntax/output, File Provider identifiers/paths, projected files, provenance strings, staged names, or agent-facing IDs.
- Do not add implicit conversion initializers, cross-type equality, or convenience APIs that accept both `PageID` and `ChatID`.
- Do not introduce a separate `ChatMessageID` in this work; retain `ChatMessage.id: PageID` and document it as deferred.
- This is a nominal-type refactor, not a visual redesign or behavior change.

# Implementation Plan

## Phase 1: Characterize compatibility and define `ChatID`

1. Add a pre-implementation characterization suite modeled on `PageIDLegacyCodableCharacterizationTests`.
   - Encode a local legacy payload type whose chat field is `PageID` and prove that top-level and nested chat IDs are primitive JSON strings.
   - Cover representative daemon contracts from `ChatXPCRequests.swift`, including an optional reply ID and a required continue/session ID. Compare normalized JSON objects, not incidental key ordering.
   - Add literal JSON fixture strings that were not generated by the new `ChatID` implementation.
2. Add `Sources/WikiFSTypes/ChatID.swift` as `Hashable`, `Codable`, `RawRepresentable`, `Sendable`, and `Identifiable`, mirroring `PageID`'s raw `String` storage and primitive-string Codable shape.
3. Do not define `init(PageID)`, `PageID.init(ChatID)`, cross-type equality, or overloaded compatibility shims. Construct `ChatID(rawValue:)` only where raw external text enters a typed chat boundary.
4. Add `ChatIDTests` for raw-value preservation, identity, hashing, and exact compatibility with the characterized legacy JSON shape.
5. Add literal daemon JSON decode-re-encode tests that prove optional and required chat ID fields retain the same normalized payloads after conversion.

## Phase 2: Convert chat domain models and mixed carriers

1. Change `ChatSummary.id` and its initializer to `ChatID` in `ChatModels.swift`.
2. Change `ChatMessage.chatID` to `ChatID`; keep `ChatMessage.id` and message-summary APIs' `messageID` as `PageID`. Add comments that identify the deferred message-ID namespace so later audits do not convert it accidentally.
3. Change tagged mixed-resource carriers to preserve namespaces:
   - `WikiSelection.chat(ChatID)`
   - `BookmarkNode.Content.chat(ChatID)`
   - `TranscriptID.chat(ChatID)` while retaining `.queueItem(QueueItem.ID)`
   - `ChatSessionKey.chat(ChatID)`, renaming its misleading `pageID` projection to `chatID`
   - Address-bar, reader-routing, provenance-navigation, and other local enums whose chat cases currently carry `PageID`
4. Preserve draft state as explicit enum/optional state (`.draft`, `.newChat`, or `ChatID?`) rather than creating a sentinel `ChatID`.
5. Update bookmark row reconstruction so `chat_ref` creates `ChatID(rawValue:)`; preserve the existing `kind`, `label`, and `target_id` columns and validation rules.
6. Update pure model and mixed-carrier tests to assert the new associated-value type and unchanged raw projections.

## Phase 3: Convert store protocols, GRDB boundaries, and model adapters

1. Change every chat-entity requirement in `WikiStore.swift` from `PageID` to `ChatID`, including append/read/rename/delete/get, summary and ACP-session updates, model overrides, streaming checkpoints, stale-draft finalization, title resolution, semantic chunks, missing embedding work, and bookmark-reference operations.
2. Keep message identity parameters as `PageID`. Where a method accepts both, require `chatID: ChatID` and `messageID: PageID` so the compiler enforces direction.
3. Update `GRDBWikiStore` and all conforming test stores/fakes in the same phase.
   - Decode `chats.id`, `chat_messages.chat_id`, `chat_chunks.chat_id`, `chat_search.chat_id`, and chat-owned foreign keys as `ChatID`.
   - Continue decoding `chat_messages.id` as `PageID`.
   - Bind `ChatID.rawValue` to the existing `TEXT` columns.
   - Convert newly generated chat ULIDs directly into `ChatID`; do not create an intermediate `PageID`.
4. Resolve ambiguous error construction. If `WikiStoreError.notFound(PageID)` is used for chat rows, introduce a typed chat-not-found case (for example `chatNotFound(ChatID)`) rather than rebuilding a `PageID` solely to satisfy an error API. Update throw sites and assertions without changing user-facing error text unless unavoidable.
5. Update `WikiStoreModel` chat catalogs, lookup methods, tab retargeting, bookmark creation, message persistence, summary/session updates, and chat search helpers to `ChatID`.
6. Preserve store mutation signaling: all changed public mutators must remain routed through the existing mutation/event seam and emit the same chat resource events with the same raw ID.
7. Add legacy SQLite fixtures that insert raw pre-change rows directly into `chats`, `chat_messages`, and relevant chat index/chunk tables, then prove:
   - rows decode into `ChatSummary.id: ChatID` and `ChatMessage.chatID: ChatID` without migration;
   - `ChatMessage.id` remains `PageID`;
   - writes preserve exact raw identifier text and existing relationships;
   - schema/user version does not change because of this refactor;
   - literal `PRAGMA table_info`, `PRAGMA foreign_key_list`, and relevant `sqlite_master` index definitions for `chats`, `chat_messages`, `chat_chunks`, and chat search/index tables match the pre-change schema contract.

## Phase 4: Convert daemon requests, sessions, and event routing

1. Change chat-valued fields in `ChatXPCRequests.swift` to `ChatID`: `ChatStartReply.chatID`, `ChatContinueRequest.chatID`, permission/config requests, `ChatSessionState.chatID`, and all other persisted-chat request/reply fields.
2. Preserve synthesized JSON keys, optionality, and primitive raw strings. Validate each changed request/reply with literal legacy payload tests from Phase 1.
3. Convert `DaemonChatHost`, `WikiDaemon`, daemon workload/client adapters, and event sinks to use `ChatID` internally. Convert raw XPC method string arguments into `ChatID` at protocol-entry boundaries only when the XPC protocol itself is string-based and compatibility requires it.
4. Convert `ChatDaemonCoordinator`, `RemoteChatSession`, `ChatSessionKey`, and session dictionaries/sets from chat-valued `PageID` to `ChatID`. Keep draft sessions in `.draft`, not in the persisted-chat namespace.
5. Convert queue/event-envelope fields only when they semantically identify a persisted chat. Keep queue item identity as `QueueItem.ID`, and keep unrelated page/message identifiers unchanged.
6. Verify routing between two chat IDs, reconnect/rehydration, continue/send/stop, permission resolution, config changes, generation state, and session eviction. Tests must prove events cannot be routed with `PageID` at compile time and wire JSON remains unchanged.

## Phase 5: Convert navigation, rendering, bookmarks, and SwiftUI surfaces

1. Propagate `ChatID` through `WikiSelection`, tab restoration/retargeting, sidebar selection, address-bar results, reader routes, provenance links, chat lists/details/transcripts, and chat autocomplete/navigation callbacks.
2. Convert `ChatDetailView`, `WikiDetailView`, `ChatsListView`, `ChatTranscriptView`, and related helper properties/closures to `ChatID?` or `ChatID` as appropriate. Preserve `nil` as the draft composer state.
3. Convert `TranscriptID.chat` to `ChatID` and retain the queue case's namespace; preserve incremental web-view identity behavior across tab switches.
4. Convert bookmark UI, drag/drop payload adapters, target pickers, and menu actions. Parse raw payload IDs into `ChatID` only after the payload's kind is known to be chat.
5. Preserve all view identity, route, title, and selection behavior. Do not synchronously write SwiftUI state from `NSViewRepresentable.makeNSView`/`updateNSView` or delegate callbacks reached during those updates.
6. Before coding this phase and again during implementation review, apply the repository's `swiftui-pro` guidance filtered to macOS 15 / Swift 6.0 and SwiftPM constraints. This nominal refactor should not introduce new UI composition, typography, or visual styling.
7. Extend existing navigation, transcript, bookmark, tab, and hosted-view tests to prove the same chat opens/restores/renders after the type change and that switching chat transcripts still triggers the correct full rebuild.

## Phase 6: Convert File Provider, links, projections, provenance, and CLI boundaries

1. Convert internal File Provider chat lookup/projection helpers to `ChatID`, including ordered chat projection and lookup by item identity.
2. Preserve File Provider item identifier strings, projected `chats/` paths, `chats.jsonl` content, filenames, and item metadata exactly. Add assertions against literal expected strings/paths.
3. Convert chat wiki-link resolution and rendering internals to `ChatID` after the `chat:` kind/tag has been parsed. Preserve `[[chat:<ULID>|Title]]` syntax and title resolution behavior.
4. Convert provenance `chat:<id>` navigation by constructing `ChatID(rawValue:)` at the tagged-string parser boundary. Preserve stored and displayed provenance text.
5. Convert `WikiCtlCore` chat commands to construct `ChatID` at argument parsing and use typed chat store APIs. Keep CLI arguments, stdout, JSON output, exit behavior, and daemon payloads unchanged.
6. Keep intentionally cross-kind search/index document IDs as raw strings or tagged enums when one field spans pages, sources, and chats; convert to `ChatID` only in a branch already known to be chat.
7. Add projection, wiki-link, provenance, and CLI regression tests that compare literal legacy-visible output.

## Phase 7: Enforce the API boundary and complete the audit

1. Extend `IdentifierBoundaryTypecheckTests` and its real-module fixtures:
   - Positive fixture: page APIs accept `PageID`, source APIs accept `SourceID`, and chat APIs accept `ChatID`.
   - Negative fixture: `PageID` passed to a chat API fails with the expected type mismatch.
   - Negative fixture: `ChatID` passed to a page API fails.
   - Add source/chat exchange fixtures where useful so all three namespaces are pairwise protected.
2. Use actual public repository APIs in fixtures, not local toy overloads. Keep module search-path setup compatible with command-line SwiftPM.
3. Add `ChatAPISignatureManifestTests` and `Tests/WikiFSTests/Fixtures/ChatAPISignatures.txt`, modeled on `SourceAPISignatureManifestTests`. List reviewed public properties/methods whose persisted-chat values must contain `ChatID`; require every entry to exist and contain `ChatID`.
4. Run a final `rg` audit across `Sources` and `Tests` for `PageID` near chat terminology. Classify every remaining hit as:
   - true page identity;
   - retained `ChatMessage.id`/message identity;
   - raw compatibility boundary;
   - test-only legacy characterization fixture;
   - unresolved chat entity identity that must be converted.
   Do not use a proximity regex as the automated correctness test and do not maintain a broad allowlist of all `PageID` occurrences.
5. Audit raw `String` chat identifiers. Keep them only at documented external/mixed boundaries; replace internal chat-valued strings with `ChatID` or an existing tagged enum.
6. Confirm no implicit conversion, overloaded page/chat compatibility method, or cross-type equality was introduced.

# Acceptance Criteria

- **AC.1** `ChatID` is public in `WikiFSTypes`, preserves the raw ULID string, and encodes/decodes with the exact primitive-string JSON shape previously used by chat-valued `PageID`.
- **AC.2** `ChatSummary.id`, `ChatMessage.chatID`, chat store APIs, and chat-owned GRDB identifiers use `ChatID`; `ChatMessage.id` remains `PageID`.
- **AC.3** Page, source, and chat APIs reject identifiers from the other namespaces in real-module compiler fixtures, with no implicit conversions or cross-type equality.
- **AC.4** Literal legacy `chats` and `chat_messages` rows load without migration, retain relationships, and write the exact same raw identifiers; schema/user version and table layout remain unchanged.
- **AC.5** Literal legacy daemon request/reply/session JSON decodes after the migration and re-encodes to the same normalized JSON object and raw ID values.
- **AC.6** Daemon hosts, app coordinators, remote sessions, event routing, reconnect/rehydration, permissions, config updates, and generation state use `ChatID` and preserve behavior.
- **AC.7** `WikiSelection.chat`, `BookmarkNode.Content.chat`, `TranscriptID.chat`, `ChatSessionKey.chat`, and other mixed carriers use `ChatID`; draft and queue identities remain separate.
- **AC.8** Chat navigation, tab restoration, sidebar/address-bar selection, provenance navigation, transcript identity/rebuild behavior, bookmarks, and rendering preserve observable behavior.
- **AC.9** File Provider item identifiers/paths/projections, chat wiki-link syntax, provenance strings, CLI inputs/outputs, daemon payloads, and agent-facing chat references remain byte-for-byte or normalized-JSON compatible as appropriate. Internal diagnostic log call sites continue to interpolate the same `ChatID.rawValue`, but exact unified-log rendering is not an acceptance contract because the repository has no deterministic `os_log` capture seam.
- **AC.10** A non-empty chat API signature manifest passes and the final audit finds no persisted chat entity API still typed as `PageID` or an untagged internal `String`.
- **AC.11** Documentation records the namespace boundary, compatibility contract, no-migration decision, raw boundaries, and deferred message-ID namespace in `plans/chat-id-separation.md`, `PLAN.md`, and `PROGRESS.md`.
- **AC.12** `make prompts`, focused tests, `swift build --build-tests`, full `swift test`, `make lint`, `git diff --check`, and CI pass using command-line SwiftPM.

# Risks, Blockers, and Required Decisions

- **Message IDs share the old type:** `ChatMessage.id` is still `PageID`. The issue asks for chat entity identity, not a new message namespace. Convert `ChatMessage.chatID` only and document message identity as deferred.
- **Broad migration surface:** Store, daemon, sessions, SwiftUI, bookmarks, rendering, projections, and CLI all carry chat identity. Work in buildable phases and use compiler errors plus the signature manifest to expose missed call sites.
- **Compatibility can regress silently:** Synthesized Codable currently emits primitive strings. Literal legacy fixtures must be captured before/independently of the new type and compared as normalized JSON.
- **Mixed raw IDs are intentional at boundaries:** Search indexes, drag payloads, XPC method arguments, links, provenance, and File Provider identifiers may carry raw strings across resource kinds. Convert only after a kind/tag identifies the chat namespace.
- **Error APIs may force false conversions:** Split ambiguous not-found errors instead of wrapping a chat raw value in `PageID` merely for reporting.
- **Draft chat state has no persisted identity:** Preserve explicit `.draft`/`.newChat`/optional state; never create a sentinel `ChatID`.
- **Test fixture diagnostics can vary by toolchain:** Match the stable type-mismatch portion of compiler output, following the existing fixture harness, rather than the entire diagnostic.
- **Skill naming mismatch:** Loaded context requests `ste-testing`, but the configured prose skill is `ste-writing`. Execution should use `ste-writing` unless the operator supplies another skill.
- No product decision or test-infrastructure blocker remains. The repository already has Swift Testing integration fixtures, real-module `swiftc -typecheck` fixtures, signature-manifest tests, GRDB fixture patterns, daemon tests, projection tests, and full SwiftPM gates suitable for this work.
