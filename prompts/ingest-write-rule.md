WRITES — READ THIS FIRST. The wiki mount is READ-ONLY BY DESIGN. NEVER write files under it and NEVER search for a "mutation tool" or test whether the mount is writable — writing the mount fails ON PURPOSE; do not probe it. The ONLY way to create or update content is the `wikictl` command. Use the PREFERRED FORM in your RUN ENVIRONMENT block with its exact wiki selector before the subcommand. Ordinary runs use `--wiki <wiki-id>`; isolated evaluation runs use `--database-path <absolute-path>` instead. Never replace or combine these selectors. Bare `wikictl` is FIRST on your PATH. If bare `wikictl` is not found, use the TRUSTED ABSOLUTE INVOCATION fallback from the RUN ENVIRONMENT block verbatim — it targets this wiki even if your nested tool moved its working directory or dropped `WIKI_DB`/`WIKICTL`/`PATH` (those are conveniences, not requirements). Deliver every body via a scratch FILE: write it under the SCRATCH WORKSPACE named in your RUN ENVIRONMENT block, then pass `--body-file <absolute-path>`. A file is the robust default for substantial Markdown; short stdin pipes (`--body-file -`) or quoted heredocs (`<<'EOF'`) also work inside the sandbox (temp files are confined beneath your scratch `.tmp`) — prefer the file for anything you may need to retry. Write with:
  wikictl page add --title T --body-file <scratch>/body.md --source <assigned-source-id>:primary
  wikictl index set --body-file <scratch>/index.md
  wikictl log append --kind ingest --title "…" --note "…"
Existing page writes add the CAS expectation; new-page writes add the create guard (never both):
  wikictl page add --title T --body-file <scratch>/body.md --expect-head <head_version_id> --source <assigned-source-id>:primary
  wikictl page add --title T --body-file <scratch>/body.md --create-only --source <assigned-source-id>:primary

Never pass `--source` on `wikictl log append` — the app records ingestion completion at job success.

After a write, read it back with `wikictl page get` (the mount lags the database by ~5s, so cat-ing the mount right after a write shows stale bytes). Cross-link pages with [[Page Title]] wiki-links.

**Updating an existing page — reconcile, don't overwrite.** When the page already exists, read its current body AND `head_version_id` in ONE `wikictl page get --json` read before composing. Preserve claims that remain supported and keep the citation of every claim you keep; incorporate the new evidence with citations of its own; qualify superseded interpretations instead of contradicting them in place; record change as history when the wiki's strategy calls for it. Never append a contradiction blindly, and never keep citations whose claims you removed.

**Version inputs:** Include the primary source and each source that supports a retained or new claim in this version. Repeat `--source '<source-id>:supporting'` for supporting inputs, including sources from earlier ingestions. Keeping a citation in the body does not record that source as a version input. Read supporting passages when needed to assess claims. Record consulted inputs honestly. Do not copy all historical provenance or citations: include only inputs used for the resulting version.

**CAS discipline:** For an EXISTING page, pass `--expect-head <that id>` from that same JSON read. For a page that does NOT exist, pass `--create-only` — it fails on exit code 3 if the page appeared since your read. The two flags are mutually exclusive; use exactly the one matching what your read found. On exit code 3 (CAS conflict), re-read the body AND head in one JSON read, RECOMPUTE your composition against the new body — never resend the old composed body with only a refreshed head — and retry once. If it fails again, report the page as failed rather than looping or claiming success. Blind upserts (neither flag) succeed unconditionally with no CAS check, as before.
