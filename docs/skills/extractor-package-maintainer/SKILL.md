# Extractor package maintainer

Read the normative references before you change a package:

- [Extractor script protocol](../../../docs/architecture/extractor-script-protocol.md)
- [Extractor package manifest](../../../docs/architecture/extractor-package-manifest.md)
- [Dynamic extractor Cordis lifecycle](../../../docs/architecture/dynamic-extractor-cordis-lifecycle.md)

## Package facts

- An extractor package is one local directory with `manifest.json` and declared files. Import accepts no archives, URLs, or remote sources.
- Protocol revision 1 is the only supported protocol revision. Use manifest revision 1 unless a package declares credential requirements. Credential requirements require manifest revision 2.
- One request enters the process. One terminal frame exits on standard output as JSON Lines.
- Supported extractor kinds are `pdf`, `html`, and `docx`. One input file, one Markdown result per operation.
- Capabilities are the closed set `network`, `shared-runtime-cache`, `model-download`. `model-download` requires `network`. A capability is a declaration, not a sandbox.
- A package runs as a one-shot process. It never runs as Swift, never provides a Cordis plugin, and never receives a `CordisContext`.

## Create or change a package

1. Copy the layout of the closest reviewed package in `ExtractorPackages/` (`Defuddle` for HTML, `Pdf2md` for PDF, `DoclingServe` for a direct-launch Python entry point, `Docx2md` for DOCX).
2. Choose a lowercase reverse-DNS `packageID`, a strict semver `version`, and stable registration IDs.
3. Declare the entry point and every file, including licenses and provenance notes. Declare no undeclared files in the folder.
4. Choose `direct` or `runtime` launch. `direct` entry points need owner-execute source permission; `runtime` scripts need only owner-read. Keep runtime arguments fixed and bounded.
5. Declare only capabilities the package truly uses. Prefer none.
6. Set operation limits at or below host policy. Start from the reviewed packages' limits.
7. Compute lowercase SHA-256 digests for every declared file and the package digest, and put them in `manifest.json`.
8. Validate: `swift run extractor-package-tool validate <folder>` from the repository root. Fix every error.
9. Smoke the protocol: `swift run extractor-package-tool protocol-smoke <folder> <request.json> <frames.jsonl>`.
10. Run `make build` and the extractor test suites before you hand the package to a user.

The validation tool does not install or activate the package. Only the app writes the machine catalog.

## Update a reviewed package

The reviewed packages are build inputs. The app and the `wikid.xpc` service receive the same `ExtractorPackages/` tree, and the catalog pins exact digests.

1. Edit the sources under `tools/defuddle/`, `tools/pdf2md/`, `tools/docling-serve/`, or `tools/docx2md/`. Do not edit generated bytes by hand.
2. Run `./scripts/sync-extractor-packages.sh` to regenerate `ExtractorPackages/`. It also refreshes `sources.lock.json`.
3. Run `make extractor-packages` (or any `make` gate; it is a prerequisite of `build`, `check`, and `test`). Drift between `tools/` and `ExtractorPackages/` must fail a gate.
4. If the package digest changed, update the golden constant in `Sources/WikiFSCore/Extractor/ReviewedExtractorPackages.swift`. `ReviewedExtractorPackageTests` fails with the digest to use.
5. Keep `PROVENANCE.md` and license files inside each package current. Declare them in the manifest so their digests are pinned.
6. Keep PEP 723 metadata and `pyproject.toml` dependencies synchronized in pdf2md.
7. Run the Python gates from `tools/pdf2md` when pdf2md changed: `mise exec -- uv run pytest tests/`, `ruff check`, and `pyright`. Run `bun test` from `tools/docx2md` when docx2md changed.

## Inspect lifecycle state

- Settings → Extraction → **Installed Extractor Packages** lists the exact revisions this process can run, with version, digest prefix, and registration.
- The reconciler retains bounded, redacted failure records: package ID, version, digest prefix, and a host-authored message. Messages never contain paths or environment values.
- `DynamicPluginHost` inspection is source-free: definition identity, fingerprint, run ID, component state history, missing dependencies, failure phase, cleanup anomalies. Use it through the extraction context, not by importing package state.
- Logs go through `DebugLog.extraction`. Never add `print`, content bytes, credentials, or unbounded stderr.

## Do not

- Do not add a second package resolver or a package-specific consumer switch. `ExtractionBackendRegistry` is the only adapter authority.
- Do not let a package declare arbitrary Cordis dependencies, services, tools, or listeners.
- Do not add shell execution, dynamic code loading, or a long-lived package daemon.
- Do not describe Cordis lifecycle or capabilities as a sandbox.
- Do not store package bytes or records in wiki SQLite, queue payloads, or the File Provider projection.
- Do not change fallback behavior. An unavailable selection keeps its saved state, emits one redacted diagnostic, and uses the reviewed or built-in fallback. Fallback never recurses into another third-party package.
- Do not merge or enqueue anything. Open a branch and a pull request. The operator owns the merge.
